1. SUMMARY - THE 12 THINGS THAT MATTER MOST
=====================================================================
 1. [NEW][LIVE] Anyone on the internet can make themselves Superadmin.
    There are several ways (section 3, items S1-S5). The simplest: sign in
    with any Google account, then send one request to /api/users or
    /api/assign-role. None of the API routes check who is calling.

 2. [NEW] Any signed-in user (default role "supporter") gets the FULL
    Admin & Operations Panel. The Navbar link was hidden, but
    app/page.tsx:572 still opens the panel for any signed-in user, and the
    Home page "Classroom" button and the settings shortcut send them there.

 3. [OPEN][LIVE] All applicant personal data (names, dates of birth, home
    addresses, phone, ID-document results) can be downloaded by anyone
    from /api/applications, and by any signed-in user straight from
    Firestore (rules allow every signed-in user to read every collection).

 4. [NEW][LIVE] The "AI Document Verification" invents results. With no
    working Gemini key (the current situation) ANY file named
    "passport.jpg" is reported as "Legitimate, 96%, verified Australian
    passport valid through 2034". Staff could accept fake identity or
    qualification documents.

 5. [NEW][LIVE] The new Multilingual RAG search is never used by the chat.
    The FAQ search before it always "finds" something, so every unknown
    question gets the "general admission requirements" FAQ as the answer.

 6. [NEW] The RAG ingest/seed/query routes are open to anyone, so anyone
    can add text that the AI will later repeat to students as fact.
    Fallback "fake" vectors are mixed with real Gemini vectors in the same
    index, which makes search results meaningless once that happens.

 7. [NEW][LIVE] The Role Permissions screen has no effect: no code anywhere
    checks those permissions. And a mistyped role name silently rewrites
    the "supporter" role's permissions.

 8. [NEW] "Assign Role & Issue Student ID" never issues a Student Number
    when "student" is picked from the drop-down (lower-case vs
    upper-case mismatch).

 9. [OPEN][LIVE] File upload lets anyone write any file anywhere on the
    server (path traversal). Confirmed again today.

10. [OPEN] The 16 Oct fix patch (rto-ai-fixes.patch, 30 fixes) was never
    applied. 18 of its 22 files still apply cleanly; 4 no longer do
    (ApplicationPortalView.tsx, lib/agent/engine.ts, lib/agent/tools.ts,
    lib/firebase/client.ts) because the code changed since. So the Unit
    Syllabuses crash, "$NaNk/yr" fees, empty "Add to Google Calendar"
    link, double-booked advisor slots, etc. are all still there.

11. [NEW] Signing in on this project rewrites the user's shared record in
    the central "users" collection (role normalised, tenantTag/databaseCode
    forced to "rto-ai"). SuperAdminRole.txt Rule 3 says this must never
    happen, because 1,000+ projects share that collection.

12. [OPEN] A lot of the admin panel only pretends to work (Google
    Classroom, Google Calendar, Tokens/Stripe, Staff Messages, Events
    editor) and important data lives only in server memory, so it is lost
    on every restart.

3. P1 - SECURITY AND PRIVACY
=====================================================================

S1. Anyone can register themselves as Superadmin through /api/users
    [NEW]  [Effort: M]
   Where: app/api/users/route.ts:118-279 (POST), lib/auth/roles.ts:197-226
   What:  POST /api/users takes "uid" and "email" from the request body and
          believes them. It never checks a Firebase ID token. If the email
          is on the hard-coded owner list (support@..., admin@...,
          eleanor.vance@edupulse.edu.au, a personal gmail) it writes
          role "superadmin" AND sets Superadmin custom claims on that uid.
          So: sign in with any Google account, copy your own uid, then
          POST {uid: <yours>, email: "support@aifoundation.net.au"}.
          Also: posting a new uid with SOMEONE ELSE's email copies that
          person's record and role onto the new uid (l.136-149).
          Also: any email matching a fictional seed account
          (scripts/seed-database.ts) inherits that seed role (l.155-163).
   Fix:   Send "Authorization: Bearer <idToken>" from the browser; on the
          server call auth.verifyIdToken() and take uid/email ONLY from the
          verified token. Never copy another document's role.

S2. Any signed-in user gets the Admin & Operations Panel  [NEW]  [Effort: S]
   Where: app/page.tsx:572 "(classroomUser || isAdminLoggedIn)";
          app/page.tsx:193-199 and :517-523 (settings shortcut and Home
          "Classroom" button go to 'admin' for any signed-in user);
          app/page.tsx:589 and :635 set isAdminLoggedIn(true) regardless of
          role; components/admin/AdminDashboardView.tsx has no role check.
   What:  A brand-new "supporter" sees Role Permissions, Assign Role,
          every application, API keys, telemetry, etc. Hiding the Navbar
          link (uncommitted change in Navbar.tsx) does not stop this.
          The panel also opens from localStorage alone: a saved
          "edupulse_user" with isSuperAdmin:true is trusted (l.66-78).
   Fix:   Gate on the verified custom claim (getIdTokenResult()), not on
          "is someone signed in", and enforce the same check on the server
          (S3).

S3. No API route checks who is calling  [OPEN cleanup #1 - now wider]
    [Effort: M]
   Where: every file in app/api/** (there is no verifyIdToken and no
          Authorization header anywhere in the code).
   What:  The Admin SDK bypasses Firestore rules, so anyone can:
          - PATCH /api/users            -> make any uid Superadmin    [LIVE]
          - POST /api/assign-role       -> same, with custom claims   [LIVE]
          - POST /api/permissions       -> grant any permission       [LIVE]
          - POST /api/course-builder    -> "prepare_superadmin", save or
                                           overwrite programs/units
          - GET  /api/users             -> every user's name and email in
                                           the SHARED users collection,
                                           i.e. users of every project,
                                           not just rto-ai (no tenant filter)
          - GET  /api/applications      -> all applicant PII          [LIVE]
          - POST /api/applications      -> overwrite any application, set
                                           status "Accepted"
          - POST/DELETE /api/faqs       -> change what the chatbot tells
                                           students
          - POST /api/rag/ingest|seed   -> add "facts" to the AI knowledge
                                           base                       [LIVE]
          - POST /api/sheets/sync       -> replace the course catalogue
          - GET  /api/telemetry         -> emails, IPs, user agents   [LIVE]
          - POST /api/tokens            -> fake ledger entries
          - POST /api/upload            -> write files (S8)           [LIVE]
          - POST /api/chat, /api/faqs/parse-bank, /api/rag/query
                                        -> spend your Gemini quota with no
                                           rate limit
   Fix:   One helper, e.g. lib/auth/requireUser.ts:
            verifyIdToken -> read role claim -> check permission
          (this is exactly what roleHasPermission() in
          lib/auth/permissions.ts was written for - it is never called).
          Keep public only: POST /api/chat, GET/POST /api/events,
          POST /api/applications (own application only),
          POST /api/telemetry - with rate limiting.

S4. Firestore rules let any signed-in user read everything, and edit their
    own role  [OPEN cleanup #4 + NEW part]  [Effort: S]
   Where: firestore.rules:146-150 (catch-all read), :114-128 (users)
   What:  - Catch-all "allow read: if isSignedIn()" means any Google account
            can read applications, chat_interactions, activity_logs,
            token_transactions, event_bookings, knowledge_embeddings...
            directly from the browser SDK.
          - [NEW] users/{uid}: the owner may update their own document

          - isSuperAdmin() checks 'SUPERADMIN'/'ADMIN' (upper case) but the
            app writes 'superadmin' (lower case), so real superadmins are
            only admins in the rules through the email-domain wildcard.
          - isAdmin() treats ANY @aifoundation.net.au / .com.au email as
            admin, with no email_verified check. SuperAdminRole.txt Rule 4
            forbids domain wildcards.
   Fix:   Deny by default; per-collection rules; block role / isSuperAdmin /
          classification / status fields in owner updates; one role
          spelling.

    [Effort: S to stop the harm, M to do properly]
   Where: app/api/applications/verify-document/route.ts:129-184 (fallback)

   What:  When Gemini is not configured, fails, or returns bad JSON, the

   Fix:   On any failure return "Not verified - manual review required".

          Correct the privacy text and mention Google processing.

P1. One way to know who the user is  [Effort: M]
    Today the "current user" is assembled in the browser from localStorage,
    a hard-coded email list and an unauthenticated GET. Replace with:
    Google sign-in -> server verifies the ID token -> server sets custom
    claims -> browser reads claims from getIdTokenResult() -> every API
    checks the token. Put it in one hook (e.g. useSession) and one server
    helper.

P2. One source of truth for courses and units  [Effort: L]
    Choose either Course Builder (Firestore) or Google Sheets / data files,
    and make the catalogue tabs, chatbot tools, Home page and Application
    Form all read from it. (If Course Builder is removed - see
    removeclassroom.txt - the data files / Sheets become that source.)

P3. Persist what matters  [Effort: M]
    Events, booked slots, applications, the synced catalogue and custom
    FAQs: store them in Firestore and use memory only as a cache. Delete the
    in-memory fake applicants.

P4. Let the AI do the understanding  [Effort: M]
    The 500-line keyword engine causes most of the wrong answers. When
    Gemini is available, let Gemini choose the tool (it already has the tool
    definitions) and keep the keyword engine only as a small emergency
    fallback. Add RAG as a tool, not as an unreachable last step.

P5. Cut Firestore and AI cost  [Effort: S]
    - Telemetry: 2 writes per event, one event per keystroke in the form,
      plus one hot "metrics/platform_stats" document (Firestore sustains
      about 1 write per second per document). Debounce, sample, or use
      Google Analytics for page views.
    - The admin telemetry tab re-reads 61 documents every 10 seconds
      (about 8,800 reads per day per open tab). Use onSnapshot or 60 s.
    - RAG embeds with 5 parallel single calls; the SDK can embed a batch in
      one call. A new GoogleGenAI client is created on every call.
    - Rate-limit the public AI routes (chat, parse-bank, rag/query).

P6. Make failures visible  [Effort: S]
    Many functions catch errors and return success:true (B14). Return the
    real outcome and show it to staff. Add timeouts (AbortController) to
    every Gemini request.

P7. Build safety  [Effort: S]
    next.config.js sets typescript.ignoreBuildErrors and
    eslint.ignoreDuringBuilds, so broken code can be deployed without
    warning. The type check passes today - turn the checks back on to keep
    it that way. Add an ESLint config (no-unused-vars would have caught
    Appendix B). "config.cache = false" turns off webpack caching
    everywhere; it is only needed on the USB stick.

P8. Tests  [Effort: M]
    There are no automated tests. The 14 live checks in Appendix A and the
    65 API / 80 browser checks from 16 Oct are a ready-made list. A small
    Vitest + Playwright suite run against the Firestore emulator would stop
    regressions and never touch production data.
    scripts/verify_strict_supporter_registration.js runs against the LIVE
    database, hard-codes a third party's email address, and leaves its test
    user behind if a check fails.

P9. Admin panel performance  [Effort: S]
    AdminDashboardView statically imports all 16 tab components (about
    11,000 lines). Load each tab with next/dynamic. /setup-mfa ships 252 kB
    of JavaScript for a page that cannot work.
